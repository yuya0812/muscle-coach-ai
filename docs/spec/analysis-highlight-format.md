# Spec: 分析出力の固定フォーマット化（ハイライト選定のコード化）

## Why（なぜ作るか）

方針転換（[ai-scope-pivot.md](ai-scope-pivot.md)）で分析は「コード集計 + AI言語化」になったが、
実機確認で「分析結果がわかりにくい」という問題が確認された。

原因は AI の言語化ではなく、**コードが渡す分析データに優先順位がない**こと。
現状の `buildAnalysisData`（analysis.ts）はセッション数・部位別刺激回数・種目別実績・
成長トレンドを均等に渡し、プロンプトは「与えられたものを箇条書きで言語化」と指示している。
結果、要点のない均等な報告書になる。

ユーザーが分析に求めるものは優先順に:
1. 「自分はちゃんと成長してるのか？」（進捗の実感）
2. 「次にジムで何をすればいいか」（行動につながる指示1つ）
3. 「このままで大丈夫か」（偏り・停滞の警告）

**「何を伝えるか」の選定（ハイライト選定）もコードの仕事にする**ことで、
「判定はコード・AIは言語化のみ」の設計原則を保ったまま出力をわかりやすくする。

## What（何を作るか）

### ユーザーストーリー

- トレーニーとして、「分析して」と送ったら要点が一目でわかる固定構成の分析がほしい。
  なぜなら、データの羅列からは「で、どうすればいいの？」が読み取れないから。

### 受け入れ条件

#### 出力フォーマット（固定・全4セクション）

- [x] 分析出力は以下の固定フォーマットで返る（ユーザー決定 2026-06-11）:
  1. **弱点** — 刺激できていない部位・著しく偏っている部位
  2. **伸びているところ** — 重量・回数が向上している種目
  3. **伸び悩んでいるところ** — 複数回実施しているが変化が小さい種目
  4. **次のステップ** — 上記から導かれる次の一歩（1点のみ）
- [x] 集計は**週区切り**で行う（今週の実績を軸に、比較は過去データと行う）
- [x] 各セクションの掲載項目は**コードが選定**する（セクションごとに上限を設け、
      優先度の高いものだけ渡す）。AIは渡された項目の言語化のみ行う
- [x] 該当データがないセクションは「該当なし」「まだ判定できる記録がない」と素直に出す
      （無理に埋めない・捏造しない）
- [x] 再現性: 同じ記録状態からは実質同じ分析が返る（既存原則の維持）

#### 適用範囲

- [x] 通常分析（「分析して」）に新フォーマットを適用する
- [x] 週次レポート（buildAnalysis 共用）にも同フォーマットを適用する
- [x] マイルストーン（5/15/30回）も同じセクション構造を使う（kind 別の焦点の付け方は
      Plan で精査）

### スコープ外

- 案B: 問いの内容による分析種別の振り分け（「伸びてる？」→ trend 等）。今回は見送り
- 案C: Flex Message・バー表現などの視覚的な構造化
- LIFF 側ダッシュボードの表示変更
- プレミアム課金軸（分析回数制限）の再設計

## 未確定事項（最大3点）

1. **「週区切り」の定義** → 仮決定: 直近7日間を「今週」とするローリング方式
   （暦週・月曜起点だと週初めに分析データがほぼ空になるため）。比較対象は
   その前の7〜14日前および全期間の実績。
2. **各セクションの選定ロジックと上限** → 仮決定: 弱点=未刺激部位を最大2部位、
   伸び=改善幅の大きい順に最大2種目、伸び悩み=最大2種目、次のステップ=
   弱点があれば弱点補強、なければ伸び悩み打開、それもなければ継続強化の1点。
3. **記録が少ない初期ユーザーの扱い** → 仮決定: 週内の記録が0件なら分析せず
   「今週はまだ記録がない」案内。週1件以上あれば、判定不能セクションは
   「まだ判定できない」と明示して出す。
